# Schema-level tile settings

**Status:** design, approved in conversation 2026-10-01
**Author:** Martin Høgh with Claude

## 1. What this is for

A GC2 database serves two kinds of tilesets. A layer's own tileset
(`myschema.mytable`, plus `.mvt` and `.json`) can be configured: which cache
backend it uses, its format, its TTL, its metatile size. The **merged
per-schema tileset** (`myschema` and `myschema.mvt`), which draws every layer in
the schema in one image, cannot be configured at all — every one of those values
is a literal in the config generator.

So an operator who tiles a whole schema has no way to put it on S3, give it a
sensible TTL, or widen its metatiles, even though the same operator can do all
three for any single layer. This closes that gap.

Success is: everything that can be set on a layer's tileset and means something
for a merged one can be set per schema, through the API and therefore from the
GUI, and an install that sets nothing generates exactly the config it generates
today.

## 2. What the code does today

`Mapcachefile::generate()` (`app/models/Mapcachefile.php`) builds per-layer
tilesets from the layer's `def` JSONB in `settings.geometry_columns_join`,
resolved by the pure `layerSettings()`: `cache`, `format`, `ttl`,
`auto_expire`, `meta_size`, `meta_buffer`, `layers`, `s3_tile_set`. Those keys
are edited through the v4 `Layer` API (`AbstractLayerApi.php`) and the legacy
`controllers/tile/{table}`.

The per-schema loop, at the end of the same method, reads nothing:

```php
$s .= self::renderWmsSource($schema, 'image/png', implode(',', $layers), $schemaUrl);
$s .= self::renderTileset($schema, $schema, $defaultCache, $gridNames, 'PNG', 60,
    metaSize: 3, metaBuffer: 0, title: $schema);
if ($mvtEnabled) {
    $s .= self::renderWmsSource("$schema.mvt", 'mvt', implode(',', $layers), $this->mapserverUrl($schema, 'wfs'));
    $s .= self::renderTileset("$schema.mvt", "$schema.mvt", $defaultCache, $gridNames, 'MVT', 60, title: $schema);
}
```

`$defaultCache` is the install-wide `App::$param['mapCache']['type']`
(default `sqlite`). `expires` is 60 seconds, `metaSize` 3, `metaBuffer` 0,
`auto_expire` absent, `abstract` empty, `title` the schema name, and there is no
way to reach the per-tileset S3 cache that layers can use.

The config is regenerated by `app/scripts/mapcache_conf.php`, which cron runs
once a minute, and `Mapcachefile::write()` only writes when the content changed.
So a settings change takes effect within a minute with no further action.

## 3. Decisions

**3.1 Scope: the merged schema tileset only.** The settings apply to `<schema>`
and `<schema>.mvt`. They are *not* inherited by the schema's layers.
*Rejected:* making them defaults that layers inherit. It is the more powerful
feature — one place to put 200 layers on S3 — but it changes what every existing
layer with an empty field does, which is a silent behaviour change on upgrade
across every install. If inheritance is wanted later it can be added on top of
this without changing the storage or the API.

**3.2 Storage: a new table, `settings.schema_settings`.** One row per schema,
with the settings in a `def` JSONB of the same shape as a layer's.
*Rejected:* `settings.key_value` under a `tile.schema.<schema>` key — no
migration needed, but the value has no schema and a mistyped key fails silently.
*Rejected:* a per-schema block in `App.php`, the way `useQgisForMergedLayers`
works today — it cannot be set from the GUI and needs a deploy per change, which
is the problem being solved.

**3.3 Settings survive dropping the schema.** Dropping and recreating a schema
is a normal workflow here, and having to set the tiling up again each time is the
irritation, not the leftover row. `Schema`'s delete does not touch
`settings.schema_settings`.
This is safe by construction rather than by care: the per-schema loop iterates
`$layersPerSchema`, which is built from actual layer rows, so a row for a schema
that does not exist is never read. It has no effect until the schema is back.

**3.4 `PATCH` requires the schema to exist now; `GET` and `DELETE` do not.** A
write to a schema that is not there is `404`.
*Why, given 3.3:* a persisted row that nothing validates is how a typo becomes a
ghost — `digi` instead of `dagi` sits inert for months and then silently takes
effect the day someone creates a schema with that name, and nothing in the
config points at the cause. Requiring the schema to exist at write time costs
nothing in the drop-and-recreate workflow, where the schema has existed before
and exists again.
Reading and deleting must *not* require it, or a leftover row from 3.3 could
never be inspected or removed through the API — the only way to see or clear it
would be SQL. So `GET` on a schema that does not exist answers the stored row if
there is one (with `schema_exists: false`, so a GUI can label it as waiting for
its schema), or the fallbacks if there is not, and `DELETE` removes the row
either way.

**3.5 Changing settings does not clear the existing cache.** Saving a form
should not delete a cache that may be large. This matches layers, where nothing
clears the cache on a `def` change either; the GUI has a separate action for it
(`DELETE /api/v4/mapcache/database/{database}/tileset/{tileset}`).
The consequence must be documented for the GUI: after changing `cache` or
`format`, already-cached tiles live in the old backend or the old format and are
neither served nor cleaned up. Clearing the tileset afterwards is the operator's
call.

## 4. The settings

The tile-relevant subset of a layer's `def` keys, plus the two metadata fields
that are currently hardcoded. Each is optional; an absent or empty value means
"use the fallback", which is what the generator emits today.

| Key | Type | Fallback | What it becomes |
|---|---|---|---|
| `cache` | string | `App::$param['mapCache']['type']` ?: `sqlite` | `<cache>` — one of `sqlite`, `disk`, `memcache`, `s3` |
| `format` | string | `PNG` for `<schema>`, `MVT` for `<schema>.mvt` | `<format>` — `PNG`, `jpeg_low`, `jpeg_medium`, `jpeg_high`, `MVT` |
| `ttl` | int | `60` | `<expires>`, floored at 30 as `layerSettings()` does |
| `auto_expire` | int | absent | `<auto_expire>`, only emitted when set |
| `meta_size` | int | `3` | `<metatile>N N</metatile>` |
| `meta_buffer` | int | `0` | `<metabuffer>` |
| `s3_tile_set` | string | absent | with `cache: s3`, gives the schema its own `s3_<schema>` cache whose object path is this value, exactly as a layer's `s3_tile_set` does |
| `title` | string | the schema name | `<metadata><title>`, what WMTS capabilities shows |
| `abstract` | string | empty | `<metadata><abstract>` |

Not included, with reasons:

- **`layers`** — for a merged tileset the layer list *is* the schema's layers,
  computed from `$layersPerSchema`. A way to restrict which layers go into the
  merged image is a different feature, out of scope (§9).
- **the styling keys** (`theme_column`, `opacity`, `cluster`, `label_*`,
  `*scaledenom`, `geotype`, `offsite`, `lock`, `bands`, …) — they configure one
  layer's mapfile, and have no meaning for a tileset that merges many layers.

`format` deserves two notes.

A schema has two tilesets of different kinds, so one `format` value cannot mean
the same thing for both: `MVT` is a raw vector format and `PNG` and the `jpeg_*`
formats are images. The resolver therefore applies the stored `format` to the
tileset whose kind it matches and leaves the other at its fallback — a stored
`MVT` changes `<schema>.mvt` and leaves `<schema>` on `PNG`, and a stored
`jpeg_medium` changes `<schema>` and leaves `<schema>.mvt` on `MVT`. The only
practical use is picking a jpeg quality for the merged image, which is exactly
the case an operator asks for on a basemap-like schema.

`JSON` is **not** allowed, though a layer may use it: there is no merged
`<schema>.json` tileset for it to apply to, so accepting it would store a value
that does nothing. It is rejected with the allowed list in the message.

## 5. How the config is generated

A new pure static beside `layerSettings()`:

```php
public static function schemaSettings(?array $row, string $defaultCache): array
```

`$row` is the `settings.schema_settings` row for this schema, or `null` when
there is none. It returns the same shape `layerSettings()` returns, so the
per-schema loop keeps calling `renderTileset()` with named arguments and nothing
else about that loop changes. Being pure and taking the row rather than reading
it makes it unit-testable without a database, which is how `layerSettings()` is
already tested (`app/tests/unit/MapcachefileRenderTest.php`).

**The fallbacks are the values in §2, not the layer ones.** This is the trap in
this feature: `layerSettings()` falls back to `expires 30`, `metaSize null` and
`metaBuffer 0`, while the schema loop uses `60`, `3` and `0`. Reusing
`layerSettings()` or copying its defaults would change the generated config on
every existing install, silently — a different TTL and a metatile element where
there was none. The requirement is therefore stated as a test, not as a
sentence: **with `settings.schema_settings` empty, the generated document is
byte-identical to the one generated before this change.**

`generate()` reads the whole table once into an array keyed by schema before the
loop, rather than querying per schema — the loop already runs over every schema
in the database and the table is one small row per schema.

## 6. API

A new v4 controller, following the existing nesting
(`api/v4/schemas/{schema}/privileges`, `.../search`):

```
#[Controller(route: 'api/v4/schemas/{schema}/tile', scope: Scope::SUPER_USER_ONLY)]
```

`SUPER_USER_ONLY`, because this is schema administration and the install-wide
cache backends it selects are not a sub-user's business.

- **`GET`** — the schema's effective settings: the stored values merged over the
  fallbacks, so a client sees what the generator will actually do rather than a
  mostly-empty object. Two extra fields serve the GUI: `_stored`, carrying only
  what is actually stored so a form can tell "set to 60" from "defaulting to
  60", and `schema_exists`, false for a row left behind by §3.3. Never 404.
- **`PATCH`** — merges the given keys into `def`; an explicit `null` removes a
  key and returns it to its fallback. Validated with a Symfony
  `Assert\Collection` where every field is `Assert\Optional`, `allowExtraFields:
  false`. `cache` and `format` are validated against the lists in §4 —
  `INVALID_REQUEST` with the allowed values in the message, the way the
  tileseeder's `UNKNOWN_GRID` names the tileset's real grids. Answers `303` with
  `Location`, as `patchResponse()` does.
- **`DELETE`** — removes the row, returning the schema to the current hardcoded
  behaviour. `204`, and `204` again when there was no row, so it is idempotent.
  Works whether or not the schema exists, which is how a leftover row is cleared.
- **`OPTIONS`** and **`HEAD`** stubs, since a browser will call this.

Error codes: `SCHEMA_NOT_FOUND` (404, `PATCH` only), `INVALID_REQUEST` (400),
`SUPER_USER_ONLY` (403).

Every action carries `OA\*` attributes and the resource gets an
`#[OA\Schema(schema: 'SchemaTileSettings')]`, so the SDK and MCP generators see
it. Request and response are **separate schemas**, as the tileseeder round
established: the response's fields are all present (merged with fallbacks) while
the request's are all optional.

## 7. The bug this feature creates, and fixes

`Tilecache::bust($layerName, $connection)` resolves which backend to delete from
by looking the name up as a *layer* and reading its `def->cache`, falling back to
the install default. Give a schema its own `cache: s3` and the existing "clear
cache" action on `dagi` will look in sqlite, find nothing, and report success —
a button that lies.

`bust()` must therefore resolve a name that is a schema (no dot, or no matching
layer) against `settings.schema_settings` before falling back to the install
default. This is part of the feature, not a follow-up: shipping the setting
without it leaves a visibly wrong clear-cache action.

## 8. Testing

**Unit, no database** (`MapcachefileRenderTest` already has the shape):
- `schemaSettings(null, 'sqlite')` returns exactly the §2 values.
- Each key, set alone, changes exactly its own output and nothing else.
- `ttl: 10` floors to 30; `ttl` absent gives 60.
- `format: 'MVT'` applies to the `.mvt` tileset and leaves the image one `PNG`.
- `cache: 's3'` with `s3_tile_set` renders an `s3_<schema>` cache element and
  points the tileset at it; without `s3_tile_set` it uses the shared `s3` cache.

**The byte-identical test**, which is the one that protects every install:
generate the document with the table empty and compare it to a fixture captured
from the current code. It must match exactly.

**API** (`SchemaTileSettingsV4ApiCest`, provisioning its own user as the other
Cests do): GET falls back before anything is stored; PATCH then GET reads back;
an explicit `null` removes a key; an unknown `cache` and an unknown `format` are
400 with the allowed values named; `format: 'JSON'` is 400 though a layer accepts
it; an unknown field is rejected (`allowExtraFields: false`); a sub-user token is
403; `PATCH` on a non-existent schema is 404 while `GET` on one answers with
`schema_exists: false`; `DELETE` returns the fallbacks and is idempotent.

**One integration check, run by hand and written down in the plan:** set
`cache: s3` on a schema, wait for `mapcache_conf.php`, and confirm the generated
`<tileset name="dagi">` names the S3 cache. The tileseeder round is the argument
for this: every automated test there passed while the feature could not produce a
tile, because nothing exercised the real artifact.

## 9. Out of scope

- **Inheritance to the schema's layers** — §3.1. Addable later on this storage.
- **Restricting which layers enter the merged tileset** — a `layers` key for a
  schema is a different feature: it changes what the merged image *is*, not how
  it is cached.
- **Clearing the cache automatically on a settings change** — §3.5.
- **Seeding a schema tileset with the new tileseeder** — already works:
  `<schema>` and `<schema>.mvt` are ordinary tilesets and appear in WMTS
  capabilities, so `POST /api/v4/tileseeder/jobs` accepts them today.
- **The bare `&` that makes the generated config invalid XML**
  (`Mapcachefile::write()`, recorded in the tileseeder spec's §15) — this feature
  reads the table, not the file, so it is not blocked by it.
